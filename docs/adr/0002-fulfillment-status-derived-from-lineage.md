# Aggregate fulfillment status is derived from lineage, not carried by events

The tracking projector computed `CartItem.fulfillmentStatus` from a static event-type → status lookup applied last-event-wins, which regressed statuses on outbox retries and left `exception` as a permanent dead end (code review 2026-07-22, findings #12/#14). We decided that domain events are facts, and the projector recomputes the aggregate status from the live lineage records (allocations, lot item statuses, package allocations and legs, shipment statuses, open roll overs, cancellations) on every projection; the same derivation philosophy rolls `UserOrder.status` up from its items' terminal states. This makes projection idempotent and order-independent by construction, makes partial states (`partiallyRolledOver`, partial confirmation) natural, and generalizes the rule `docs/schema-reference.md` already mandates for exceptions: "return to the summary implied by current detailed records".

Considered options: keep the lookup table and add a monotonic-rank guard (smaller change, but keeps two sources of truth and needs a special branch per new event); hybrid per phase (two projector migrations instead of one). Consequence: every new fulfillment capability extends the derivation function and its evidence queries instead of registering a target status.
