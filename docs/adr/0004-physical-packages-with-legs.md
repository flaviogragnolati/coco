# Packages are physical and carry an inbound/outbound leg

A Package always represents a physical bundle and carries a leg discriminator: `inbound` (supplier → destination) or `outbound` (destination → end user). Quantity conservation against demand allocations is checked per leg, so destination fractionation never double-counts. Traceability granularity is an operational choice with an automatic default: registering a supplier dispatch consolidates the whole supplier order into one inbound package, and manual split/consolidate actions designate the real physical bundles only when the detail matters. Fractionation creates outbound packages (one per customer by default, multi-customer allowed for group pickup points); a mono-customer inbound package is promoted to the outbound leg preserving its identity.

We rejected the logical-first model (one anticipated package per customer riding both legs) because the operation needs to represent the supplier's real bundles — receipt control, partial dispatches, damaged bulk — and a package must not exist before it physically does. Consequences: a small schema migration (leg enum on `package`), the conservation diagnostics gain leg scope, and `package.shipment.missing` applies only to `inTransit` (an outbound package received with no shipment is a legitimate depot pickup).
